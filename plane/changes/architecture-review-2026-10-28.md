# 架构合理性与内存、吞吐评估

日期：2026-10-28。评估基线：fdd9d08 后端优化、b0405c3 前端第一阶段；本批收尾版本 2.2.18。详细实验分别见 [池性能首批](pool-memory-throughput/plan.md)、[后续五项](pool-memory-throughput/followup.md)、[前端审计](frontend-audit/plan.md)。本文件是评估记录，当前实现以 docs/architecture.md 为准。

## 判断与取舍

单一 Go 二进制内嵌 sing-box、SQLite WAL、控制面 HTTP 与 WebUI 的形态适合单机代理池：部署与恢复简单，没有跨进程状态同步；数据面不可变快照与控制面串行生命周期，方向合理。成员谓词、节点身份、测量与诊断、持久化写入口已经形成明确边界，应保留。当前证据不足以支持引入微服务或更换数据库，这些改造会新增一致性与运维成本。

代价是资源和故障域共处：大规模控制面查询、分组重叠与 GC 可影响转发；SQLite 写事务是串行资源；蓝绿期间同时持有新旧实例。不能只用选路 ns/op 判断整个系统吞吐。

## 本批测量

`cd frontend; node scripts/benchmark-runtime-logs.mjs` 直接从 fdd9d08 提取旧合并函数，与阶段一和当前真实 helper 比较。Windows amd64 / Node 24.21，单个同步突发，三轮中位数：

| 事件数 | 原逐条合并 | 阶段一批处理 + slice | 本批环形缓冲 + 缓存键/时间 |
| --- | ---: | ---: | ---: |
| 1000 | 227.010 ms | 0.476 ms | 0.382 ms |
| 10000 | 4200.573 ms | 24.082 ms | 1.958 ms |

10k 输入时阶段一满队列后有 9000 次 1000 引用的切片复制，本批消除此项，保留最后 1000 个到达项。基准包括构造键/时间、入队、合并与排序，不包括 SSE 解码、React/DOM、网络或 GC 存活堆测量；不把约 92% 的本地 CPU 时间下降解释为整机吞吐提升。原始输出在忽略目录 `.tools/frontend-audit/log-benchmark-results.json`。

此前本地 CONNECT/echo 的前后独立进程中位吞吐 3642.0 → 3614.6 MiB/s，短时差异没有证明端到端吞吐提升；内存收益与选路成本收益分别报告。下一阶段容量验证应在部署用 Linux 上按实际协议、组重叠率和长连接比例做独立负载进程的持续测试，采集 RSS、分配速率、GC CPU、连接建立 p95/p99、有效载荷吞吐、错误率和健康欠账。profile 默认关闭、开启后仍要求本机与管理会话；见 [性能操作说明](../../docs/performance.md)。
