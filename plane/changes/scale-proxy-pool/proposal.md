# 大型代理池基础设施：变更提案

状态：**Proposed**。已有主路径按代码基线锁定，实施任务尚未验收。入口：[文档索引](../../README.md)；当前约束：[spec](../../specs/proxy-pool/spec.md)。

## Why

EasyProxiesV2 已具备节点汇聚、身份修订、健康收据、分组隔离、容量规划和有界自愈。下一步需要把这些能力变成可规模运营的单机基础设施：容量不足能解释，故障恢复受预算约束，导入与策略更新不污染运行态，运营人员能通过 UI、审计和指标闭环。

服务对象为多订阅、多地区、多标签、多组的代理池运营方。核心结果是可预测的出口容量与安全变更；容量无法满足时应准确呈现不足原因，不能承诺没有候选时仍保持可用。

## What changes

| 类型 | 能力 | 本提案范围 |
| --- | --- | --- |
| MODIFIED | IDENTITY-001 / HEALTH-001 / DIAGNOSTIC-001 | 生产入口写路径审计、导入交错与诊断隔离回归，收敛可旁路接口 |
| MODIFIED | HEAL-001 / HEAL-002 | 执行前重读与审计矩阵、预算观测、后续可配置化，保持现有 PlanHealing / Healer |
| ADDED | SCALE-001 | 探测及事件投递容量模型、过载与排队指标、固定场景压测 |
| ADDED | OPS-001 | 缺口原因、策略变更追踪、持续告警与 dry-run 引导 |
| MODIFIED | RUNTIME-001 / AUDIT-001 | 大候选集增量变更验证、独立保留期清理、备份恢复演练 |
| ADDED，后期可选 | PLATFORM-001 | 多实例权威状态、权限及金丝雀的独立 RFC |

ADDED 项仅为未来规格增量，定义见 [设计](design.md#拟新增规格增量)，验收见 [验证计划](validation.md)；未合并到当前 spec，不能据此宣称实现已完成。没有 REMOVED 项；不改候选资格、健康来源、恢复阈值等核心语义。

## 非目标

- 不重写 Runtime、PlanHealing、Healer、Applier 或现有探测执行器。
- 不为“分层”立即迁移到 `httpapi/controlplane`，也不把 L0–L5 机械映射为六个新包。
- 不引入分布式共享 SQLite、多实例同时管理同一池、租户隔离或新的消息总线。
- 不在本批文档任务改变 API、数据库、默认执行开关或发布版本。

## 规模假设与承诺边界

下面是**待压测验证的候选验收环境**，不是当前产品承诺。阶段 0 先记录实际主机、网络和超时参数；首次跑数后确认或调整门槛，并保留理由。

| 项目 | 候选基线 | 扩展场景 |
| --- | --- | --- |
| 节点 / 分组 / 订阅 | 1,000 / 50 / 20 | 5,000 / 200 / 100 |
| 单组候选与重叠 | 100–1,000；共节点比例 50% | 全量重叠及热点订阅 |
| 主机 | Linux amd64，4 vCPU、8 GiB、SSD，单实例 | arm64 同资源对比，明确差异 |
| 健康网络 | 可控 mock：20–500ms 延迟，0/10/50% 失败 | 100% 硬超时、慢订阅、慢事件订阅者 |
| 探测并发 | 自动值 `min(N, clamp(ceil(N/10), 32, 128))` | 显式配置上限场景；不得假定所有入口共用同一全局限额 |
| 周期间隔 | 基准 5min，热点组 1min，共节点取适用最短间隔 | 根据超时容量公式调整，保留过载场景 |

真实公网订阅、出口质量和流量不属于确定性压测 fixture；性能报告必须区分 CPU/存储成本、模拟网络和真实网络结果。

## 路线图与交付依赖

| 阶段 | 估算工作量 | 交付与进入下一阶段的条件 |
| --- | --- | --- |
| 0 契约与基线 | 3–5 工作日 | 事件映射、写路径审计、规模假设与现状差异；文档已准备但 M1 仍需测试证据 |
| 1 写路径硬化 | 1–2 周 | 导入/身份/诊断/自愈矩阵与 race，生产旁路已分类或收敛；M1 |
| 2 规模化 | 1–2 周 | 预算可观测、队列过载方案、基准报告；M2 |
| 3 运营控制面 | 1–2 周 | 缺口解释、策略追踪、关闭执行语义；M3 |
| 4 稳定性 | 1–2 周 | 无谓重启检测、连接存续、备份恢复及清理；M4 |
| 5 平台化 | 单独估算 | 仅在单机结果不足且需求明确后提交 RFC，不阻塞 M1–M4 |

估算是小团队排期起点，不是发布日期。阶段 3 的只读解释与 dry-run 引导可在阶段 1 并行；阶段 2 的优化必须先有正确性基线；多实例依赖阶段 4 的恢复与观测证据。

## 成功标准

- M1：测量、状态机和快照没有未经说明的旁路；旧身份结果不能推进恢复；有完整验证记录。
- M2：约定 N/M/S 下队列等待、完成率和 deferred 有上界或明确过载结果，自愈不放大订阅请求。
- M3：运维仅通过组视图和审计即可解释缺口、调整政策并验证关闭执行，不需要查库或读源码。
- M4：高频策略/成员变更不重启无关入口；备份和恢复按剧本执行且状态可解释。

任何里程碑都需要 [证据模板](validation.md#证据模板)；“测试文件存在”“UI 显示成功”“有告警日志”均不足以单独完成验收。

## 风险与取舍

保留节点级全局剔除/恢复，但 UI 必须解释跨组影响；保留现有分钟窗口预算，产品化时明示它与严格滑动限流的区别；先测量 `HealingInputs` 成本再引入缓存，并为身份、规则、地区、健康和成员变化设计失效；健康事件是恢复计数输入，不能直接丢弃或简单 last-value 合并。所有调整以现有契约和回归矩阵为前提。
