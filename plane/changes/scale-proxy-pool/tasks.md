# 实施任务与里程碑

状态：Proposed。任务由当前代码增量演进；现有模块不重建。复选框只表示本计划已完成的交付，已有历史测试不自动勾选。每项完成时附提交、测试命令、结果及限制，采用 [验证证据模板](validation.md#证据模板)。

## 阶段 0：基线冻结（3–5 工作日）

责任：控制面/状态机负责人，质量协作。

- [x] P0.1 建立 plane 入口、当前契约、提案、分层设计、任务和验证结构。产物：[索引](../../README.md)、[spec](../../specs/proxy-pool/spec.md)。
- [x] P0.2 静态映射四类事件、身份与代际、合法写入入口和现状差异。产物：[设计](design.md)、[审计清单](../../write-path-audit.md)。
- [x] P0.3 补全 dry-run、缺口原因及关闭执行手册；注明审计去重、保留期与在途请求限制。产物：[手册](../../group-healing.md)。
- [ ] P0.4 确认 N/M/S、部署主机、流量与探测预算；采集改动前 CPU/内存/队列/DB 基线。产物：带环境的首份报告；依赖 P0.1。
- [ ] P0.5 人工复核实际生产调用链、兼容入口和历史文档差异，冻结评审清单；高风险项有 owner 和完成条件。依赖 P0.2。

退出条件：P0.4/P0.5 完成。文档已创建不等于基线已压测冻结。

## 阶段 1：写路径硬化与回归（1–2 周）

责任：状态机、探测与质量；依赖 P0.5。覆盖 IDENTITY-001、HEALTH-001、DIAGNOSTIC-001、MEMBERSHIP-001、HEAL-001/002。

- [ ] P1.1 对照审计表分类直接 setter、真实拨号失败、人工恢复、初始注册与持久化恢复；收敛未经授权的生产调用，保留有意的测试/兼容路径。产物：调用者表及代码差异。
- [ ] P1.2 固定时钟覆盖重复导入、交错订阅、同名不同身份、A→B→A、旧 tag/旧收据晚到、取消后返回；明确 Topology 方法编排契约，只有确有需要才提出统一 envelope。
- [ ] P1.3 扩展 EVICTED × 延迟/测速/解锁/质量成功矩阵，断言健康、剔除、恢复 streak 不变；另验证诊断引发标签/地区重算仍遵守候选规则。
- [ ] P1.4 验证 dry-run 仅审计、不占预算；planned 审计失败不执行；完成审计失败可发现；Promote 二次 Plan；关闭策略及规则变化与执行竞态。
- [ ] P1.5 验证新鲜度边界、未来时间证据、多组共节点剔除/恢复、恢复阈值与冷却、共享预算、分钟窗口边界、订阅失败/熔断/重启冷却。
- [ ] P1.6 运行全量测试及关键包 race，完成人工 dry-run→执行→关闭场景；填充矩阵证据。产物：M1 报告，依赖 P1.1–P1.5。

M1：写路径分类无遗漏、回归绿且有 CI/本地可复现结果，未执行项不得写为通过。

## 阶段 2：规模化探测与调度（1–2 周）

责任：探测/调度、性能与质量；正确性改动依赖 M1，采样可提前。覆盖 SCALE-001。

- [ ] P2.1 梳理 batch/standalone/导入初检/自愈/诊断的并发归属、lease 与优先级，记录最短适用组 interval 和取消规则；确定是否需要统一总闸门。
- [ ] P2.2 暴露 Healer 窗口消耗、延期、退避和订阅熔断状态，再设计可配置参数及校验、持久化、热更新和安全默认。禁止只在 UI 加输入框。
- [ ] P2.3 测量健康事件 FIFO 的 queue_depth/oldest_age，提出有界且保留失败窗口/恢复计数语义的方案；覆盖慢消费者、溢出、重放和停止，不直接丢事件。
- [ ] P2.4 记录 HealingInputs 调用次数/扫描数/耗时/分配；仅在成本证据成立时实现按组查询或摘要缓存；补所有事实失效、新鲜度和二次执行校验。
- [ ] P2.5 增加 N×M×订阅场景、可控延迟和失败分布的 fixture/benchmark；输出优化前后事件回放等价结果和门槛报告。依赖 P0.4、P2.1–P2.4。

M2：目标场景无无限积压，预算不随组数放大，延迟和 deferred 可解释；超载场景明确降级语义。

## 阶段 3：运营控制面（1–2 周）

责任：控制面/API、运营与前端；只读视图可与 P1 并行，执行控制依赖 P1.4。覆盖 OPS-001。

- [ ] P3.1 定义后端统一组摘要 DTO：观测健康、规划健康、active/standby、缺口、初检/过期/冷却、最近动作及预算原因；附采样时间及版本，避免前端另算健康。
- [ ] P3.2 接入分组运维视图和原因解释，展示共节点剔除/恢复的全局影响；API/预览/池实际成员交叉验证。
- [ ] P3.3 沿用已有 min/target/refill 校验；新增策略变更审计，区分与自愈动作审计，记录前后值及可信操作者来源，不记录敏感订阅。
- [ ] P3.4 定义持续缺口、预算耗尽与熔断告警的持续窗口、结构化原因、去重及恢复通知；日志、UI、未来 metrics 口径相同。
- [ ] P3.5 完成安全默认、dry-run 引导和关闭执行说明；验证关闭后不再开始额外动作，区分已在途与正常周期请求。附运维演练和 UI 证据。

M3：非开发运维可从视图发现缺口、判断原因、调整策略并确认结果，不依赖扫库。

## 阶段 4：数据面、存储与热更（1–2 周）

责任：数据面、存储与质量；依赖 M1/M2，运维演练与阶段 3 协作。

- [ ] P4.1 高频 Promote/成员变化验证 PrepareUpdate/Commit、通知顺序和无 listener/base box 重启，覆盖失败回滚与重试。
- [ ] P4.2 大组场景验证 nil previous/显式空选择、稳定 active 槽位、standby 恢复状态和长连接存续；不得仅凭健康数判通过。
- [ ] P4.3 基于已有 WAL/读写分离度量写锁等待、checkpoint 与审计清理成本；实现可取消的独立清理任务，验证无新事件组的保留期。
- [ ] P4.4 制定一致性备份/恢复剧本和恢复验证；明确停机备份或 SQLite 在线备份方式、配置版本、恢复后初检及数据库不兼容降级限制。
- [ ] P4.5 覆盖组政策/探测参数热更与运行态、API、预算的一致性，完成重复变更和恢复演练。产物：M4 报告。

M4：频繁微调不造成入口闪断；连接证据、备份完整性与恢复后的状态解释齐备。

## 阶段 5：可选平台化（另立 RFC）

责任：平台/架构；仅在 M1–M4 和单机容量报告后启动，覆盖 PLATFORM-001。

- [ ] P5.1 设计统一 metrics 导出与可选远程日志，控制标签基数和敏感信息。
- [ ] P5.2 独立 RFC：权威状态外置/主从、领导权和 fencing、全局预算、故障切换；禁止直接把现有 map 改为共享变量。
- [ ] P5.3 独立 RFC：角色权限、多租户隔离和完整操作审计。
- [ ] P5.4 独立 RFC：版本化配置、金丝雀组与回滚剧本；验收包含数据库兼容与故障注入。
