# 变更提案：健康事件日志与游标投递

状态：**已实现，待合入 specs 当前契约**。基线 `dca180f`（2.2.5），本批目标 2.2.6。

## 为什么现在做

[2026-10-23 稳定性审计](../../stability-audit-2026-10-23.md) 复现了健康事件投递的真实损失：每个订阅一条容量 4096 的内存 FIFO，溢出即丢弃，而 pool 消费者用这些事件推进分组失败窗口与恢复 streak，**不是只刷新 UI 的观察者**。已复现的事实：

- 丢弃成功事件 → 已剔除节点的恢复进度永久停在 1/2，直到下一次探测；
- 丢弃失败事件 → 恢复进度不被重置，故障窗口少计一次；
- `SnapshotOnly` 标记同样会丢，不能当可靠投递屏障；
- 关闭清空待处理事件，积压无法恢复。

旧注释把这条路径写成 "lossless"、"同步回调"、"丢弃只是多刷新一次"，三处都与代码不符。审计给出的独立改造建议（把权威状态转移与可合并快照通知分开）需要持久化接口、迁移与游标语义，因此单独立项，不混入同批的订阅/重载局部修复。

## 目标

1. 健康测量的**权威状态转移**写入持久化有序日志，与测量事实同一事务提交；进程重启或在途丢失后可从日志补齐。
2. 订阅按**明确游标**有序消费日志；通知只负责唤醒，不承载事实，因此通知丢失不再等于事实丢失。
3. 同一事件重复投递/重放**不得**重复推进恢复计数或重复计入失败窗口。
4. 日志容量与背压显式化：容量满时**拒绝新的健康测量提交并报错**，不静默丢弃旧事实。
5. 积压、最老事件年龄、投递/重放/空洞/失败计数、各消费者游标可观测。

## 非目标

- 不改变失败窗口、恢复阈值、冷却等状态机语义，也不改变“诊断不发布健康事件”（DIAGNOSTIC-001）。
- 不承诺跨进程/多实例一致性：多个 manager 共用同一数据库不在此门禁保证内（同审计 S2 的边界口径）。
- 不用日志替代 `node_probe_receipts`：收据仍是“最新一条待投影结果”的幂等载体，日志是“有序历史”。
- 不引入外部消息队列、不新增部署组件；存储层仍是同一 SQLite。
- 不解决审计“仍需后续核查的静态风险”三条（订阅设置原子性、全量重载后 outbound 拓扑同步、跨代排队事件的消费者侧验收）。

## 影响面

| 层 | 改动 |
| --- | --- |
| `store` | migration v24 新建 `health_events`、`health_event_cursors`；新增 6 个方法 |
| `probe` | 健康测量的 `Apply` 事务内追加日志行；`Outcome.Seq`；容量满返回显式错误 |
| `monitor` | `healthEventHub` 改为游标投递 + 可合并刷新标志 + 持久消费者游标 + 统计 |
| `group` | 健康成功/失败入口按 ProbeID 幂等 |
| `outbound/pool` | 以稳定 key 注册持久消费者 |
| `httpapi` | `GET /api/operations/health-events` 暴露统计 |

## 回滚

删掉 `SubscribeDurableHealthResults` 调用即退回进程内直投语义（实证见 `design.md` §7）；两张新表只增不改，回滚代码后成为不被读取的死数据，不影响 v23 及以前的读路径。
