# 分组容量自愈

本文是当前自愈主路径的操作手册。架构契约见 [spec](specs/proxy-pool/spec.md)，基础设施增量计划见 [proposal](changes/scale-proxy-pool/proposal.md)。下面描述已有行为；统一缺口摘要、预算配置面板和完整政策变更审计仍在计划中。

分组字段 `min_healthy`、`target_size`、`healing_enabled`、`refill` 可在分组编辑器设置。要求 `0 <= min_healthy <= target_size`；`target_size=0` 关闭容量管理。新增/旧分组默认不执行动作。设置目标容量但保持 `healing_enabled=false` 时为 dry-run，只写拟执行动作日志。

## 活动与备用

统一成员规则先产生候选集；显式排除、地区和标签优先级不变。启用执行后，流量快照最多选 `target_size` 个活动节点，其余为备用。备用仍保留拨号器、周期健康探测、剔除状态与恢复计数；现有连接不因转为备用而被关闭。

冷启动按稳定节点 ID 初始化活动槽位。增量更新保留已有槽位；健康不足时优先保留健康活动节点，再提升健康备用节点。健康证据必须已完成初检、可用、非临时继承、没有黑名单，且测活时间不超过 `max(60秒, 2×分组测活间隔)`。未检测或已过期的证据不计健康。

## 调谐与限流

调谐器启动后立即运行，之后每 30 秒运行一次；每轮最长 2 分钟。动作按 `promote_standby` → `probe_quarantined` → `refresh_subscription` 执行，可逐项关闭。每阶段重新读取当前政策与状态，执行入口再次校验。复检不跳过恢复冷却，也不降低连续成功阈值。不会放宽任何成员规则。

- 备用提升使用已有 PrepareUpdate/Commit，快照发布后再通知状态事件，不重启监听器或 base box。
- 复检共用正常健康路径，全局最多 20 次/分钟，同一节点至少间隔 1 分钟。
- 订阅刷新全局最多 2 次/分钟，同一订阅至少间隔 5 分钟；最近尝试时间在联网前落库，重启后仍遵守冷却。仅刷新已启用订阅，候选为空时也可发现新节点。
- 动作失败指数退避；订阅连续失败 3 次后熔断 30 分钟。忙碌/策略变更记为暂缓。跨分组共享资源预算与去重，每轮轮换起始分组。
- 剩余健康数不足时写告警。每次动作记录计划、结果或暂缓原因；审计写入失败时不启动该动作。

## 观察与升级

分组卡片显示备用状态和自愈记录。认证接口 `GET /api/groups/{groupID}/healing-events?limit=50` 返回最新记录；每组最多保留 500 条及 30 天，5 分钟内相同动作和结果去重。migration v19 新增策略列与审计表。先观察 dry-run 日志，再启用实际执行；关闭执行即可停止额外动作并恢复全部候选参与流量选择。

本地实现后的编译、测试和跨架构验证统一进行；日志和 dry-run 不能替代最终验证。

## 从 dry-run 到执行

1. 确认候选规则和预览，选择 `min_healthy`、`target_size` 与所需 refill 动作，遵守 `0 <= min_healthy <= target_size <= 100000`。不要用显式成员绕过原有地区/标签运营政策。
2. 保持 `healing_enabled=false`，观察正常周期探测收敛后的多轮 dry_run 记录。dry-run 可以写审计，不能额外复检、刷新订阅或改变活动槽位；容量限制在启用执行后才生效。
3. 确认订阅可达、候选来源正确、缺口原因已解释，再对小范围分组开启执行。对比真实活动成员、健康数与审计；planned 或规划健康数不代表动作成功。
4. 观察 promote、复检、必要时补货后的真实状态；恢复复检仍需要冷却结束和足够连续成功，不因一次诊断成功恢复。
5. 扩大范围前完成 [验证计划](changes/scale-proxy-pool/validation.md) 的共享预算、关闭执行和连接存续演练。

`target_size=0` 关闭容量管理；`target_size>0` 但执行关闭是 dry-run。二者都不能等同于停用正常健康探测。

## 如何排查容量缺口

当前先从分组卡片、成员/备用状态和自愈日志联合判断；统一原因聚合视图是阶段 3 交付，不能假定现在已有对应 API 字段。

| 观察 | 含义 | 操作 |
| --- | --- | --- |
| 健康候选少于 min | 规则候选不足或来源不足 | 检查 explicit/excluded、地区/标签/筛选与订阅启用状态；不靠自愈放宽规则 |
| 有 Available 但不计健康 | 初检未完成、provisional、过期、黑名单或非 ALIVE | 核对正常探测与时间；诊断成功不能替代新鲜测活 |
| 有健康 standby 但缺口仍在 | 尚未提升、动作关闭、计划改变、忙碌或执行失败 | 查看 promote 的 planned/result，比较当前实际成员，不能只看 projected |
| EVICTED 长期存在 | 冷却中、恢复关闭、成功次数不足或再次失败 | 检查恢复政策与共享节点影响，不用手动测速推进恢复 |
| deferred：budget/backoff/busy | 共享分钟预算、同资源冷却、退避或执行竞争 | 等待到期并检查其他组，不用循环手动触发冲破预算 |
| refresh 失败/熔断 | 网络/来源故障，失败达阈值暂停 | 修复订阅；2/min、同订阅 5min、3 次失败 30min 的边界以实际窗口为准 |
| planned 后无完成结果 | 请求在途、取消、进程中断或完成审计失败 | 核对真实成员/订阅状态与进程日志，不能自动认定成功或安全重放 |
| alert 持续出现 | 观测活动健康仍低于 min | 结合上列原因处理；周期 alert 不等于已实现持续窗口告警产品 |

订阅刷新允许从已启用来源发现新候选，即使当前候选为空；新增节点仍需通过同一成员规则和健康检查，不保证刷新即补齐。

## 关闭、回滚与审计限制

关闭 `healing_enabled` 后，后续阶段及执行入口会重读并拒绝新动作，当前实现恢复全部候选参与流量选择。已经开始的网络请求不保证立即取消；正常周期和用户操作仍可能产生探测/刷新，因此观察时应记录来源及关闭时刻。强取消保证尚待专项设计和测试。

回滚政策先关闭执行，再恢复原 min/target/refill 并核对实际成员。节点级剔除/恢复会影响共节点组，不能只验证一张组卡片。数据面已有连接的存续需要专项演练，不能用日志推断。

自愈审计状态包括 dry_run、planned、succeeded、failed、deferred、alert。planned 写入失败阻断动作；完成结果的审计失败不回滚已发生的外部动作。5min 相同状态及详情去重，所以记录不是每次尝试的完整账本，也不能用于精确动作计数。30 天/每组 500 条清理发生在追加新记录时；独立过期清理属于阶段 4 计划。

备份和降级必须考虑 SQLite migration；运行中不能只复制 `.db` 忽略 WAL。当前 WAL 和读写连接分离已经启用，备份恢复工具与演练是独立交付。
